The switches in `cppdefs.h` only take effect when you rebuild the model.

!!! warning
    **Copy the output aside first if you want a comparison.** Both runs write to `CROCO_FILES/croco_his.nc`, so a rivers run overwrites a tide-only one in the same directory. Save the existing output before you rebuild:

```bash
    cd ~/seaforward/forecast/scratch/Canary_12
    mkdir -p no_rivers
    cp CROCO_FILES/croco_his.nc no_rivers/
```

    Or run both through the driver, which tags the output folders and keeps them apart — see the `--rivers` section later in this chapter.

```bash
cd ~/seaforward/forecast/scratch/Canary_12
conda deactivate
source ~/seaforward/env.sh
which nf-config          # must be .../opt_seq/bin/nf-config
./jobcomp 2>&1 | tee compile_rivers.log | tail -5
cp croco croco_plain_tides_rivers
```

`./jobcomp` runs the build; `2>&1 | tee compile_rivers.log` shows the output and saves
it. It takes a few minutes. Success looks like a small ASCII crocodile and:

```text
CROCO is OK
```

!!! warning
    **Compile outside conda**, as in Phase 2. `conda deactivate` first so the linker uses `opt_seq`'s NetCDF; with the environment active the build can pick up conda's instead. The `which nf-config` line is the check.

The `cp` matters for the driver, which selects its binary by name.

**Which name depends on what else is switched on.** If you followed Phase 10, `TIDES`
is still defined in `cppdefs.h`, so this build has both tides and rivers and the binary
is `croco_plain_tides_rivers`. For rivers alone you would turn `TIDES` back off, rebuild,
and get `croco_plain_rivers`. Check before renaming:

```bash
grep -n "^# define TIDES\|^# undef  TIDES" cppdefs.h | head -2
```

Skip the rename and the driver reports `binary not found`.
